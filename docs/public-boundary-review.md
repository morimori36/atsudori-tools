# 公開境界のレビュー

このアプリは、利用者が登録するデータと宣言的な定義を処理する独立したアプリです。特定の名前の禁止一覧ではなく、実装の独立性と持ち込む情報の由来を確認します。名称を伏せたり改名したりするだけでは、境界を守ったことになりません。

通常の監査は、このリポジトリのルール・コード・架空テストと変更内容を使って完結させます。他リポジトリへのアクセス、外部の監査設定、利用者からの別の監査依頼を必要条件にしません。

## 判断基準

- 取得元・変換先・非公開の生成工程を知ることなく、公開された契約と架空データだけで実装を説明・検証できること。
- 外部形式固有のフィールド対応、履歴生成、取得処理、接続設定を実装に埋め込まないこと。対応が必要な場合は、既存の限定された宣言的な定義の範囲で扱い、任意コード実行や未対応値の推測を追加しないこと。
- 名称・URL・識別子・コメント・例・データ構造から、特定の取得元や変換先を前提とした運用を持ち込んでいないこと。
- 実マスタ、実ランク定義、個人データ、原本、実測fixtureを含めないこと。架空の例は独立に作成し、実データの改名・一部置換で作らないこと。
- 外部コード・素材・依存ライブラリを追加するときは、由来と利用条件を確認すること。必要な権利表示は保持し、関連を隠すために削除しないこと。境界と両立しない場合は、そのコード・データの採用を見直すこと。

## 改修から公開まで

1. 変更前に上記の境界を確認する。新しく持ち込むコード・データ・素材・依存ライブラリの由来と適用条件を確認する。由来不明のものや、公開に必要な許諾を確認できないものは追加しない。計算方法の参考と、具体的なコード表現・データの利用を区別する。
2. ローカルで改修し、必要な型検査・単体・Schema・ブラウザ検証を行う。最新ソースから`npm run build`を行い、`npm run audit:public`を実行する。
3. 変更ファイルだけでなく、ビルド成果物、同梱データ、ファイル名、ブランチ名、コミットメッセージ、公開予定のPRタイトル・本文をレビューする。CIのログ・添付物も対象とする。
4. 担当エージェントが判断基準に沿って差分・成果物を内容レビューし、問題の修正・再検査まで続ける。特に、固有形式の埋込み、実データの改名、一見汎用的な例や説明による依存の持込みを確認する。名前の検索だけで合格にしない。
5. 自動検査と内容レビューを両方確認してから、許可された範囲でpush・PR作成する。変更後は対象が変わるため、必要な検査をやり直す。PRには対象コミット、検査成否、内容レビューの結論、未確認範囲を安全に説明できる形で記載する。公開できない資料・具体的な検出内容・未修正の問題をPRやCIへ転載しない。

`npm run audit:public`はファイル・履歴・配信物に対する汎用的な機械検査です。由来・権利・独立性の判断は上記の内容レビューで補います。機械検査の成功を完全な保証として扱いません。判断に必要な情報が不足する場合は、該当する追加を見送り、成立する部分の改修と検証を進めます。人間の判断が不可欠な事項だけを理由とともに報告し、監査全体を別の依頼へ振り分けません。

監査の通過は、本番デプロイ、マージ、公開設定変更、履歴書換えの承認を兼ねません。既存の承認条件を維持します。
