# 素材別充足日数シミュレーター

現在庫・育成目標までの必要量と、通常プレイの継続的な日平均供給から、素材ごとの充足日数を概算します。必要素材は共通育成条件と `calculateMaterialRequirementsToTarget()`、在庫比較は `materialInventoryBalances()` を再利用します。所持・在庫を変更しません。

主な結果は「素材・必要量・現在庫・不足量・日平均供給・充足日数」の6列です。供給源別の内訳・確実性・根拠も展開できます。開始日・終了日・試算期間・期末在庫・期末不足・将来の在庫推移・時系列明細はありません。

## 日平均供給

- ライブは毎日のLBを指定割合で通常・スキップへ分けます。スキップLBは日ごとに切捨て、残りを通常へ配分します。報酬定義の倍率・1LBあたり報酬と、入力した回数/日の報酬を合算します。直接EXP・権利は素材在庫へ換算しません。回数未入力で回数報酬がある場合は未確認です。
- 練習は「1日の蓄積時間÷受取までの蓄積時間」を平均受取回数/日とします。完全な1受取サイクルに対し、蓄積単位・上限・通常効率時間・超過効率・ランク倍率・報酬倍率を適用し、定義された受取単位／蓄積単位の切捨てと抽選回数の丸めを行った後で日平均化します。日末や任意期間末の端数受取を仮定しません。日次の蓄積時間より受取間隔が長くても計算できます。
- T.G.Wのデイリー報酬は「毎日受取る」がONなら1回/日です。練習のランク倍率と独立に設定します。
- その他の継続報酬は、外部定義の受取間隔（日数の分数）と入力した継続的な受取率（整数0〜100%）を使います。「1回分の報酬÷間隔×受取率」が日平均です。受取間隔が不明なら推測しません。月ごとの報酬も日数換算の確認済み根拠が必要で、アプリが30日などで補いません。
- 抽選報酬は重みと抽選回数による期待値です。「確認済み報酬の平均」「抽選期待値」「イベント推計」を内訳で区別します。平均に小数を残し、画面表示の丸めを充足日数の計算へ戻しません。

一度きり・課金・期間限定報酬は継続供給から除外します。パス、ショップ／シール交換、スター支出、経済効果の評価・最適化もありません。通常プレイのスターが素材資源として定義されていれば、その供給だけは同じ方式で扱えます。

## 標準イベント

外部の standardEvent は intervalDays（正整数の開催間隔）、basis（仮定の根拠）、cumulative（累計全回収分）、limited（個数制限商品全回収分）を持ちます。未登録はnull。全回収報酬÷開催間隔を1日平均へ加算します。10日間隔は暫定仮定で、外部定義から変更できます。

生成側は累計全回収分と個数制限商品だけを集約し、バッジ自体・余剰分・無制限交換を除外します。全回収はパスなしで達成する前提です。実際のイベントID・予定・到達pt・商品の購入操作は管理しません。イベント供給は推計であり、確定した日次報酬ではありません。

## 充足日数と未確認

不足量＝max(0,必要量−現在庫)。不足があり供給が正なら、充足日数＝ceil(不足量÷日平均供給)です。計算は分数で合算し、最後の切上げまで浮動小数点の誤差を持ち込みません。各素材を独立に算出し、素材の相互変換や調達手段の最適化をしません。

- 必要量・在庫が既知で既に充足済み：0日。追加供給が不要なので供給不明でも0日です。
- 不足があり継続供給が0：現在の条件では充足不可。
- 必要量・在庫・必要な供給条件が不明：算出不可。未知を0と扱いません。

需要に未計算の育成項目がある場合は既知分を小計として表示し、全体の必要量・不足・充足日数は未確定とします。供給の未確認項目は影響する素材について日平均全体を未確認とし、既知の小計と理由を残します。推計は現在の条件が続く場合の概算であり、正確な達成日や抽選での到達確率を保証しません。

## データ契約と保存

供給はcatalog内の supplyDefinition.schemaVersion=4。日時オフセット、リセット時刻・曜日・日付、開催期間はありません。fixedSources は id/name/basis、intervalDays（正のnumerator/denominator、未確認はnull）、rewardsを持ちます。継続対象と確認できる無課金報酬だけを生成してください。各rewardsはfixed・lotteries・unavailableです。

試算条件はschemaVersion=5、保存キーは atsudori-tools.economy-scenario.v5。期間日付と受取総回数を削除し、includeRankDaily と fixedSources[].claimPercent を使います。結果Exportはv4で、日平均内訳を持ち、日付・期間収支・時系列明細は持ちません。条件の保存・Import/Exportと結果のExport、使用版・育成条件・根拠の記録を維持します。

旧条件v1〜v4は非対応です。自動変換・上書きせず、元JSONのExport後、新形式Importまたは確認付きの初期化で復旧します。供給の旧v3以前も非対応です。catalog/collection本体の既存形式・登録在庫は維持します。

Private側のコード・元データは今回変更していません。生成側は供給v4に対応し、旧パス／有料定義に加えutcOffsetMinutes、fixedSourcesのreset/windowを除去し、確認済みの継続間隔intervalDaysへ明示的に置き換える必要があります。期間限定の元データを単にwindow削除で継続報酬にしてはいけません。旧生成物はそのままImportできず、新契約での実データ結合検証は未実施です。

実マスタ・個人情報を同梱せず、公開検証は独立した架空データです。

試算条件はランク・イベント、ライブ・スキップ、スタジオ、その他の継続供給に分けます。直接EXP用回数・イベントの前提・条件JSON操作は補足を開いて操作します。結果には日平均・期待値・推計の区分と未確認事項を表示し、詳細な前提と根拠は展開して確認できます。素材行は素材在庫と同じ単位順・表示順です。有効な条件変更は自動保存・再計算します。結果を先に表示し、試算条件への相互リンクで調整できます。


## 入力と保存の体験

数値・ON/OFFは共通フォーム部品を使います。数値は各入力時に整数・範囲を確認し、有効な条件のみ即時保存します。必須数値の空欄や不正値は下書きとして残し、aria-invalidと近接理由を表示します。ランク・直接EXP回数・バンド練習Lvの空欄は未確認で、0には置き換えません。入力欄自体は再描画せず、結果部分だけを更新し、内訳の展開状態を保ちます。

保存はatomicに行い、失敗時には確定条件と結果を維持します。未反映の下書きがある間は結果に「変更前の確定条件」と明示します。元のv5保存キー・JSON形式・Import/Export・確認付き初期化は維持し、旧形式・破損データを自動上書きしません。

継続供給の受取率は100%=供給源1回分の全回収、0%=除外、50%=総報酬の半分という平均近似です。日次達成率や段階到達率ではありません。標準イベントとは独立し、未指定の供給源は0%です。Premium等を利用するかは受取率の入力で指定します。1〜99%も保存・再編集できます。

6列表にはcaption・列/行見出し・名前付きのキーボード操作可能な横スクロール領域を設け、素材名と列見出しを固定します。表示丸めは算術へ戻しません。長い根拠は詳細に、未確認理由は既定展開で示します。
